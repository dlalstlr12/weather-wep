# Phase 1 구조 리팩토링 (2026-10-14)

Phase 0에서 만든 테스트를 안전망으로 구조를 정리했다. 의도한 동작 변경은 아래 "동작이 바뀐 부분"에만 있고, 그때마다 테스트를 함께 고쳤다.

## 구조 변화

| 대상 | 전 | 후 |
|---|---|---|
| `KmaClient` | 303줄, 현재/예보 두 메서드에 URL 조립·캐시·파싱·기준 시각 계산이 중복 | 91줄. 단계별 클래스로 분리 |
| 분리된 클래스 | - | `KmaBaseTime`(43), `KmaCache`(31), `KmaApiClient`(84), `KmaResponseParser`(63), `KmaApiException`(34) |
| `ChatService` | 224줄, "도시 → 좌표 → 날씨 조회"가 3곳에 복붙, 컨트롤러가 쓰지 않는 `stream()` 포함 | 128줄. `Question`/`Lookup` record와 조회 메서드 하나 |
| 위치 해석 | `WeatherService` 두 메서드에 임시 프리셋 복붙 + `ChatService`에서 별도 지오코딩 | `LocationResolver` 한 곳 (`GeoService`는 11개 도시 맵) |
| 예외 응답 | 처리 핸들러 없음 | `GlobalExceptionHandler`가 `ProblemDetail`로 변환 |
| 테스트 | 45개 | 66개 |

- 기준 시각 계산(`KmaBaseTime`)과 캐시(`KmaCache`)는 `Clock`을 주입받아, Phase 0에서 어려웠던 경계 테스트(00~01시는 전날 23시, 초단기실황 40분 기준, 자정 직후)를 추가했다.
- `KmaApiClient`가 `data`(공공데이터포털)와 `hub`(API Hub)의 URL·인증(헤더/쿼리) 차이를 한 곳에 가둔다.

## 동작이 바뀐 부분 (Phase 0에서 확인된 결함의 수정)

| 항목 | Phase 0 | Phase 1 |
|---|---|---|
| 부산이 아닌 도시 조회 | 모두 서울 좌표(60,127) | 자기 좌표 (대구는 89,91) |
| 지원하지 않는 도시 | 서울 날씨를 그대로 반환 | 400 `지원하지 않는 도시입니다` |
| 좌표와 도시명이 함께 올 때 | 도시명이 좌표를 덮어씀 | 좌표 우선 |
| 실황 응답에 SKY가 없을 때 | `NullPointerException` | 하늘 상태 `-` |
| 기상청 `resultCode` 오류 | "파싱 실패"로 감싸져 코드 소실 | `KmaApiException(RESULT_CODE)`에 코드 보존 |
| 컨트롤러 예외의 HTTP 응답 | 모두 403, 빈 본문 | 입력 오류 400 / 기상청 오류 502(`kind` 포함) / 그 외 500 |
| 로그인 실패, 중복 가입 | 403, 빈 본문 (같은 경로라 추정, Phase 0에서 직접 측정하지는 않음) | 400, 메시지 포함 (직접 확인) |
| 오류 메시지·로그의 URL | 서비스키가 포함된 전체 URL | URL 제외, endpoint만 |
| 챗: 날씨 조회 실패 시 | LLM 프롬프트를 만들며 같은 조회를 한 번 더 실행 | 조회 1회 |
| 챗: 현재/예보 키워드 동시 | 경로마다 다름 | 현재 우선 |
| 예보 기준 날짜 | 서버 시간대 | `Asia/Seoul` |

프론트 API 클라이언트는 `ProblemDetail`의 `detail`을 오류 메시지로 쓰도록 한 줄을 고쳤다.
`SecurityConfig`는 `/error`를 허용한다. 알 수 없는 경로에 인증 없이 접근하면 여전히 403이다(인증 필터가 먼저 막음).

## 재측정 (Phase 0과 같은 환경, 각 시나리오 1회)

| 시나리오 | Phase 0 | Phase 1 |
|---|---|---|
| 정상 | 200, 지연 med 6ms / p95 14ms | 200, med 6ms / p95 20ms |
| 업스트림 500 | **403**, 지연 med 38ms / p95 71ms | **502** (`kind=HTTP_ERROR`), med 5ms / p95 18ms |
| resultCode 오류 | **403**, med 37ms / p95 69ms | **502** (`kind=RESULT_CODE`), med 6ms / p95 12ms |
| 깨진 JSON | **403**, med 37ms / p95 70ms | **502** (`kind=PARSE_ERROR`), med 6ms / p95 10ms |
| 업스트림 5초 지연 (60 VU) | med 5.0s / p95 10.0s, `/` 요청 med 4.5s | 같음 (med 5.0s / p95 10.0s, `/` med 4.5s) |
| 같은 키 동시 50요청 | 업스트림 50회 | 같음 (50회) |

- 가용성 문제(타임아웃, 재시도, 서킷 브레이커, 동시 요청 합치기)는 Phase 2의 대상이라 그대로다. 이 단계에서 달라진 것은 오류의 **형태**다.
- 장애 응답의 지연이 줄어든 것(약 38ms → 5ms)은 처리되지 않은 예외마다 전체 스택트레이스를 남기던 로그가 한 줄 WARN으로 바뀐 영향으로 보이지만, 로깅 외 요인을 분리해 측정하지는 않았다. 같은 20초 동안 처리한 장애 요청 수는 약 1만 건에서 약 2.4만-6만 건으로 늘었다.
- 원본: `perf/results/phase1-*.json`
