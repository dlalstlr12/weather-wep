# Phase 2 외부 API 안정성 (2026-10-14)

기상청이 느리거나 실패해도 서비스가 스레드를 붙잡히지 않고, 가능하면 지난 값으로라도 응답하도록 만들었다.
Phase 0에서 측정한 같은 장애 시나리오로 다시 측정해 전후를 비교했다.

## 호출 경로

```
요청 → 위치 해석 → 캐시(Caffeine, 키: 격자+기준 시각)
        ├ ttl 안: 캐시 값 응답
        └ ttl 지나거나 없음: 같은 키는 한 요청만 기상청 호출 (나머지는 그 결과를 기다림)
              → 재시도(최대 2회 시도) → 서킷 브레이커 → HTTP(연결 1초, 응답 2초) → 응답 파싱
              ├ 성공: 캐시에 저장
              ├ 자료 없음(NO_DATA): 바로 앞 기준 시각으로 한 번 더 조회
              └ 실패: 3시간 안의 지난 값이 있으면 stale=true로 응답, 없으면 오류(502/503)
```

| 장치 | 동작 |
|---|---|
| 타임아웃 | 연결 1초, 응답 2초 (`kma.http.*`) |
| 재시도 | 연결 실패/타임아웃, HTTP 5xx, resultCode 05(게이트웨이 타임아웃)만. 총 2회 시도, 200ms부터 지수 백오프. 4xx, 파라미터·인증 코드, 호출 한도(22, 23), 자료 없음은 재시도하지 않음 |
| 서킷 브레이커 | 최근 20회 중 10회 이상 호출됐고 실패율 50% 이상이면 10초간 호출 차단(`CIRCUIT_OPEN`). 이후 3회 시험 호출. 실패로 세는 것: 연결 실패, 5xx, 파싱 실패, resultCode 04/05/22/23. 4xx와 자료 없음은 세지 않음 |
| 캐시 | Caffeine, 최대 1,000건, ttl 10분, stale 허용 3시간. 같은 키 동시 요청은 호출 하나로 합침. `nocache=true`는 우회(합치지도, 지난 값으로 대체하지도 않음) |
| 슬롯 폴백 | 현재 기준 시각의 자료가 없으면(resultCode 03 또는 빈 결과) 바로 앞 발표 슬롯으로 한 번 더 조회 |
| 응답 | `stale`, `ageSeconds` 필드 추가. 챗은 "N분 전 데이터" 안내, 화면은 안내 문구 표시 |
| 오류 응답 | 연결 불가·차단 503 / 응답은 받았지만 쓸 수 없음 502 (`kind` 포함) |

설정은 모두 `application.yml`의 `kma.*`에 있다.

## 측정 환경
Phase 0, 1과 같다 (한 PC, 백엔드 `java -jar`, MySQL·k6는 Docker, 기상청은 WireMock). 차이점:
- **시나리오마다 백엔드를 새로 띄운다** (`perf/run-isolated.sh`). 서킷 브레이커·캐시 상태가 다음 시나리오로 넘어가면 결과가 오염된다 (처음 한 번 그렇게 돌려 이를 확인했고 버렸다).
- 캐시 ttl을 2초로 줄여 실행했다 (`--kma.cache.ttl-seconds=2`). stale 시나리오를 만들기 위한 설정이며, 다른 시나리오는 `nocache`로 캐시를 우회한다.
- 전체를 **2회** 반복했다 (run1, run2). 값이 크게 다른 항목은 둘 다 적었다.

## 결과 (Phase 1 → Phase 2)

| 시나리오 | Phase 1 | Phase 2 (run1 / run2) |
|---|---|---|
| 정상 (20 VU, 20초) | 200, 지연 med 6ms / p95 20ms | 200, med 6 / 7ms, p95 17 / 21ms (회귀 없음). 업스트림 호출 = 요청 수 |
| 업스트림 500 | 502, 요청마다 업스트림 1회 호출 | 502 → 503, **업스트림 호출 20 / 20회** (요청 1,987 / 701건). 지연 med 12 / 14ms |
| resultCode 22 | 요청마다 호출 | 업스트림 호출 **133 / 36회** (요청 3,044 / 1,966건) |
| 깨진 JSON | 요청마다 호출 | 업스트림 호출 **36 / 17회** (요청 498 / 1,598건) |
| 업스트림 5초 지연 (60 VU, 30초) | 200, 지연 med 5.0s / p95 10.0s, 무관한 `/` 요청 med **4.5s** | 대부분 503으로 즉시 응답 (med 15 / 13ms), 처음 몇 건만 타임아웃까지 대기(max 2.3s). 무관한 `/` 요청 med **2ms**. 업스트림 호출 **53 / 53회** (요청 3,667 / 3,634건) |
| 캐시가 빈 같은 키에 50개 동시 요청 (업스트림 1초 지연) | 업스트림 **50회** | 업스트림 **1 / 1회**, 50건 모두 200 (약 1.0s) |
| ttl 경과 후 업스트림 500 (**신규**, 캐시가 채워진 키, 20 VU) | stale 폴백이 없어 오류 (코드 기준, Phase 1 빌드로 같은 측정은 하지 않음) | 요청 75,743 / 77,999건 중 75,724 / 77,999건이 **200 + `stale:true`** (run1의 19건은 실패), med 4ms. 업스트림 호출 11 / 11회 |

해석:
- **스레드가 묶이는 문제가 해결됐다.** 5초 지연에서 날씨와 무관한 요청이 4.5초에서 2ms로 돌아왔다. 타임아웃(2초)과 서킷 브레이커가 요청 스레드를 붙잡지 않기 때문이다.
- **장애 중 업스트림 호출이 요청 수의 1-7% 수준으로 줄었다.** 장애 시나리오에서 업스트림 호출이 요청 수와 같던 것이 17-133회로 줄었다. 횟수가 run마다 다른 것은 서킷 브레이커가 열리기 전에 이미 들어온 동시 요청 수와 시험 호출 시점이 달라서다.
- **같은 키 동시 요청이 호출 하나로 합쳐졌다** (50 → 1).
- **장애 중에도 응답한다.** 캐시에 값이 있었다면 지난 값을 `stale`로 표시해 200으로 준다.

## 한계와 주의
- **느리지만 정상인 업스트림이 이제 실패로 처리된다.** Phase 1은 5초 걸려도 결국 200을 줬지만, Phase 2는 2초 안에 응답이 없으면 끊는다. 실제 기상청 응답 시간은 이 환경에서 측정하지 못했다 (기상청 키 없이 WireMock으로만 측정). 타임아웃 값은 실제 응답 시간을 재서 조정해야 한다.
- 장애 시나리오의 **요청 건수는 Phase 1과 비교하지 않는다.** 503 응답에서 연결이 끊겨(Tomcat이 일부 오류 상태 코드에서 keep-alive를 끊는 것으로 보이며, 직접 확인하지는 않았다) k6가 매번 새로 연결하게 되어 Docker Desktop 환경에서 연결 시간이 지연에 섞였다. 지연 분포(`http_req_duration`)와 업스트림 호출 수는 이 영향을 받지 않는다.
- 일부 run에서 설명하지 못한 소수의 실패가 있었다 (정상 시나리오의 부하 도구 쪽 연결 문제로 의심, 한 run의 `/` 요청 1건과 stale 시나리오 19건). 확인하지는 못했다.
- 재시도가 있어 최악의 경우 요청 하나가 약 4.2초 (2초 × 2회 + 백오프) 스레드를 쓴다.
- 서킷 브레이커는 JVM 하나에 하나이고 엔드포인트·격자를 구분하지 않는다. 캐시도 서버 메모리라 인스턴스가 늘면 인스턴스마다 따로다.
- `resultCode 03`이 "자료 없음"이라는 것은 공식 문서에서 확인하지 못했다 (공통 코드표에서 05, 22, 23은 확인). 빈 결과도 같이 자료 없음으로 취급해 폴백이 동작하게 했다. 발표 직후 몇 분 동안 자료가 없는지도 확인하지 못했다.
- 서킷 브레이커 상태 전이는 로그로만 남는다. 지표는 Phase 6에서 추가한다.

원본 수치: `perf/results/phase2-*.json`(run1), `phase2-r2-*.json`(run2), 업스트림 호출 수는 `*.upstream.json`.
