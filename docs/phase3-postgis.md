# Phase 3 PostgreSQL + PostGIS (2026-10-14)

MySQL을 PostgreSQL(PostGIS)로 바꾸고, 하드코딩된 도시 11곳 대신 기상청 행정구역 격자 표 3,836곳으로 위치를 찾도록 했다.

## 변경 요약
- DB: MySQL 8 → PostgreSQL 16 + PostGIS 3.4 (`postgis/postgis:16-3.4`). 드라이버, Flyway 모듈, Hibernate 설정, docker-compose 교체. `jdbc.time_zone`은 UTC.
- 마이그레이션: V1, V2는 PostgreSQL 문법으로 다시 작성(DB를 새로 만들기 때문에 기존 체크섬과 충돌하지 않음), 사용하지 않던 `weather_cache` 테이블은 만들지 않음.
  - V3: `postgis`, `pg_trgm` 확장과 `locations` 테이블(GiST 공간 인덱스, 이름 trigram GIN 인덱스, 격자 인덱스)
  - V4: 기상청 행정구역 격자 3,836행 적재
- 위치 검색: 이름 검색(`ILIKE`), 반경 검색(`ST_DWithin`), 가장 가까운 지역(KNN `<->`). `/api/locations/search`, `/api/locations/nearby`.
- 위치 해석: 도시명은 위치 테이블에서 찾고, **표의 기상청 공식 격자(nx, ny)를 그대로 사용**한다. 좌표로 요청하면 기존처럼 변환식으로 계산한다. `GeoService`(11개 도시)는 삭제.
- 테스트: Testcontainers로 실제 PostGIS에서 마이그레이션, JPA 매핑, 공간 쿼리, 실데이터 검증 (97개 → 119개).

## 데이터
- 출처: 기상청 [단기예보 조회서비스](https://www.data.go.kr/data/15084084/openapi.do) 오픈API 활용가이드의 '격자 위경도' 엑셀 (공공데이터포털). 이용허락범위 **공공누리 제1유형(출처표시)**. 첨부 엑셀에 별도 조건이 있는지는 확인하지 못했다.
- 파일: `기상청41_단기예보 조회서비스_오픈API활용가이드_격자_위경도(2607).xlsx`, 시트 `최종 업데이트 파일_20260701`.
- 변환: `tools/generate_locations_migration.py` (원본 엑셀은 저장소에 넣지 않았고, 생성된 V4 SQL만 커밋).
- 구성: 3,838행 = 시·도 18, 시·군·구 256, 읍·면·동 3,564. 행정구역코드는 모두 유일.

데이터에서 확인한 것:
- **이어도 2행은 경위도가 0**이라 제외했다. 3,836행을 적재.
- `전북특별자치도 전주시덕진구 금암동` 1행은 도분초 컬럼과 십진 도 컬럼의 위도가 약 0.0027도(약 300m) 다르다. 십진 도 컬럼을 썼다.
- 2026년 자료에서는 광주광역시가 **`전남광주통합특별시`**(전남 시·군 포함)로 바뀌어 있다. 그래서 `광주` 검색은 이 지역을 돌려준다.
- **좌표에서 변환식으로 계산한 격자가 공식 격자와 다른 곳이 43곳(1.1%)** 이다 (한 칸 차이). 예: 서울 강북구 수유1동은 공식 60,128, 계산 61,128. 이름으로 찾은 지역은 표의 값을 그대로 쓰는 이유다.

## 검색 동작
- 이름 검색은 `full_name`(예: `서울특별시 강남구 역삼1동`)에 대한 부분 일치이고, 정렬은 상위 행정구역 우선 → 이름이 짧은 순이다.
- `%`, `_`는 일반 문자로 처리한다.
- 동명 지역은 구분하지 못한다 (`중구`는 5곳). 이름이 짧은 순이라 하나만 골라진다. 모호한 이름은 Phase 4의 챗 도구에서 후보를 보여주는 방식으로 다룰 예정이다.

## 인덱스 효과 (EXPLAIN ANALYZE)
PostgreSQL 16.4 + PostGIS 3.4, Docker 컨테이너 하나. 쿼리를 **같은 psql 세션에서 8번 실행하고 첫 번째는 버린 7회의 중앙값**이다.

### 실제 행정구역 데이터 (3,836행)
`LocationRepository`가 쓰는 SQL을 그대로 사용 (`perf/postgis/run_real_benchmark.py`, 결과 `results-real.txt`).

| 쿼리 | 인덱스 없음 | 인덱스 있음 | 배율 | 계획 |
|---|---|---|---|---|
| 반경 5km, 서울 (밀집) | 5.31 ms | 0.245 ms | 21.7배 | Seq Scan → Bitmap Index Scan |
| 반경 5km, 인제 (희소) | 6.06 ms | 0.046 ms | 131.7배 | Seq Scan → Index Scan |
| 가장 가까운 1곳, 서울 | 4.09 ms | 0.160 ms | 25.6배 | Seq Scan → Index Scan |
| 가장 가까운 1곳, 인제 | 6.06 ms | 0.057 ms | 106.4배 | Seq Scan → Index Scan |
| 이름 검색 '역삼' (ILIKE) | 2.38 ms | 2.60 ms | 효과 없음 | Seq Scan (인덱스가 있어도 플래너가 선택하지 않음) |

3,836행은 작아서 절대 시간 차이는 몇 ms이지만, 공간 인덱스는 이 크기에서도 계획을 바꾸고 20-130배 빠르다. 이름 검색의 trigram 인덱스는 이 크기에서는 쓰이지 않는다.

### 합성 데이터 (균등 분포 무작위 점, `perf/postgis/run_benchmark.py`)
| 행 수 | 반경 5km | 가장 가까운 5개 |
|---|---|---|
| 3,800 | 4.96 → 0.04 ms (118배) | 1.85 → 0.06 ms (30배) |
| 100,000 | 140.79 → 0.16 ms (880배) | 54.65 → 0.31 ms (175배) |
| 1,000,000 | 567.53 → 0.60 ms (940배) | 232.60 → 0.20 ms (1,163배) |

실제 행정구역은 도시에 몰려 있어 균등 분포와 다르다. 행 수가 커질수록 인덱스 없는 쿼리는 선형으로 느려지고, 인덱스 쿼리는 거의 일정하다.

**측정 방법을 고친 이력**: 처음에는 쿼리마다 psql 세션을 새로 열어 측정했는데, 새 세션의 첫 호출에 PROJ/SRID 캐시 초기화 비용(약 8ms)이 섞여 인덱스 쿼리가 모두 약 9ms로 나왔다 (1M행 반경 검색 9.8ms 등). 같은 세션에서 반복해 다시 측정한 값이 위의 표이고, 앞의 값은 폐기했다. 커넥션 풀을 쓰는 서버에서는 이 초기화 비용이 연결당 한 번만 든다.

## 앱 수준 확인 (로컬, 기상청은 WireMock)
- 기동 시 Flyway가 4개 마이그레이션을 적용하고 앱이 정상 기동.
- `city=대구`로 날씨를 조회하면 기상청에 공식 격자 **89,90**으로 요청이 나간다 (Phase 1의 계산값은 89,91). 제주 52,38, 역삼 61,125.
- 존재하지 않는 지역은 400 (`찾을 수 없는 지역입니다`).
- `/api/locations/search?q=역삼` 300회 연속 호출: 중앙값 7.4 ms, p95 9.7 ms. `/nearby` (반경 5km): 중앙값 4.4 ms, p95 6.0 ms (HTTP 포함, 한 PC에서 측정).

## 배포 전환 절차 (Railway + Render)
기존 Render 서비스는 MySQL을 쓰므로, 새 코드를 배포하기 전에 새 DB를 준비해야 한다.
1. Railway에서 **PostGIS 템플릿**(PostgreSQL 16, PostGIS 3.4)으로 새 DB를 만든다. 외부(Render)에서 접속해야 하므로 공개 접속 정보(TCP 프록시 호스트와 포트)를 쓴다.
2. Render 환경변수를 바꾼다: `SPRING_DATASOURCE_URL=jdbc:postgresql://<호스트>:<포트>/<DB이름>`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD`. `JWT_SECRET`은 그대로 둔다.
3. **초기 배포 때 넣었던 임시 환경변수가 남아 있지 않은지 확인한다.** 트러블 슈팅 문서에 `SPRING_FLYWAY_ENABLED=false`, `SPRING_JPA_HIBERNATE_DDL_AUTO=update`가 기록돼 있다. 남아 있으면 마이그레이션이 돌지 않거나 스키마가 어긋난다.
4. 이 PR을 머지한다. `postgis` 확장은 Flyway V3가 `CREATE EXTENSION`으로 만든다 (템플릿의 기본 사용자가 슈퍼유저여야 한다).
5. 머지와 환경변수 변경은 가까운 시점에 한다. 둘 중 하나만 적용된 중간 배포는 기동에 실패할 수 있다. Render는 새 배포가 헬스 체크를 통과하지 못하면 이전 버전을 유지하는 것으로 알고 있지만 이 환경에서 확인하지는 않았다.
6. 배포 후 `/api/locations/search?q=서울`이 결과를 돌려주는지 확인한다. 기존 가입자는 모두 사라지므로 다시 가입해야 한다.

## 한계
- 이름 검색은 부분 일치이고 동명 지역을 구분하지 못한다. 형태소·오타·초성 검색은 없다.
- Railway 계정의 요금제와 한도, PostGIS 템플릿이 만드는 DB의 접속 변수 이름은 확인하지 못했다.
- 템플릿 DB의 사용자가 `CREATE EXTENSION`을 할 수 있는지는 배포해 보기 전에는 확신할 수 없다.
- 행정구역 격자 표는 정기적으로 갱신된다 (이 파일은 2026-07-01 기준). 갱신은 수동으로 `tools/generate_locations_migration.py`를 다시 돌려 새 마이그레이션을 추가해야 한다.
- 서버 측정은 모두 한 PC에서 한 것이다.
