# Phase 7 챗 스트리밍과 문서 정리 (2026-10-18)

챗 화면이 완성된 답을 한꺼번에 받는 대신, 도구를 조회하는 동안 상태를 보여 주고 답변을 조각으로 받아 그리도록 바꿨다. 아울러 README를 재구성하고 문서 목록과 트러블슈팅을 정리했다.

## 1. 진짜 스트리밍
이전의 `/api/chat/stream`은 완성된 답을 만든 뒤 240바이트씩 잘라 보내는 가짜 스트리밍이었다. 이제 Anthropic의 스트리밍 응답(`stream: true`, SSE)을 읽어 글자 조각을 그대로 브라우저로 흘려 보낸다.

### 서버가 보내는 이벤트 (SSE, 데이터는 JSON)
| 이벤트 | 데이터 | 의미 |
|---|---|---|
| `status` | `{ text }` | 도구를 조회하는 중 ("현재 날씨를 조회하는 중이에요", "예보를 조회하는 중이에요", "지역을 찾는 중이에요") |
| `delta` | `{ text }` | 답변 글자 조각 |
| `reset` | `{}` | 지금까지 받은 답변 조각을 지운다 |
| `done` | `{}` | 끝 |
| `error` | `{ message }` | 오류 |

- **reset이 필요한 두 경우**: ① 모델이 도구를 부르기 전에 문장을 흘려 보냈을 때(도구 호출은 그 문장 뒤에 시작된다) ② 스트리밍 도중 모델 호출이 실패해 규칙 기반 답변으로 바꿀 때. 보낸 조각이 있을 때만 보낸다.
- **LLM을 못 쓰는 경우**(키 없음, 한도 초과, 실패, 호출 횟수 초과)에는 규칙 기반 답변 전체를 `delta` 한 번으로 보낸다. 화면은 같은 코드로 처리한다.
- **연결이 끊기면** 전송이 실패해 `StreamClosedException`이 올라오고, 더 이상 모델을 부르지 않고 도구도 실행하지 않는다. 이 경우는 `chat_requests_total{path="llm",reason="cancelled"}`로 센다.
- 토큰, 도구 호출, 처리 경로 측정값은 기존 비스트리밍 경로와 같이 쌓인다 (스트림의 `message_start`와 `message_delta`에서 토큰 수를 읽는다).
- 비스트리밍 `POST /api/chat`은 그대로 있고, 평가(Phase 5)는 이 경로를 쓴다.
- 스트리밍 작업은 공용 풀이 아니라 전용 스레드 풀에서 돌린다 (모델을 기다리는 블로킹 작업이라). 동시 챗 수는 일일 사용 한도가 제한한다.

### 화면 (`ChatPage`)
- 처음에는 "응답 생성 중...", 도구를 쓰면 서버가 보낸 상태 문구, 답변이 오기 시작하면 상태를 지우고 글자를 이어 붙인다.
- 내용이 생기기 전의 빈 말풍선은 그리지 않는다. 오류가 나면 빈 말풍선이 남지 않고 같은 말풍선이 오류 문구로 바뀐다. 취소 버튼으로 응답을 끊을 수 있다.

## 2. 확인한 것 (로컬, 실제 Claude Haiku 5.5, 기상청은 대역)
**서버 직접 호출** (8개 질문, 각 1회):

| 구분 | 첫 이벤트(상태) | 첫 글자 | 전체 | 첫 글자 → 전체 |
|---|---|---|---|---|
| 도구를 쓴 6개 질문 | 0.73 ~ 1.57초 | 1.55 ~ 3.15초 | 1.86 ~ 3.55초 | 0.26 ~ 0.53초 |
| 도구 없이 답한 2개 (거절, 위치 되묻기) | 0.77, 1.01초 | 0.77, 1.01초 | 1.22, 1.27초 | 0.45, 0.26초 |

**브라우저** (실제 챗 화면, 질문 "내일 부산 비 와?", DOM 변화를 기록): 0초 "응답 생성 중..." → 0.98초 "예보를 조회하는 중이에요" → 2.29초부터 2.81초까지 답변 94자가 28번에 걸쳐 늘어남.

해석:
- 사용자는 1초 안팎에 "조회 중" 상태를 보게 되고, 답변은 마지막 0.3~0.5초 동안 흘러나온다. 답변이 1~2문장이라 글자 흐름 자체의 이득은 작고, **체감 개선은 주로 상태 표시**다.
- 비스트리밍 경로와 같은 조건으로 나란히 비교한 측정은 하지 않았다 (Phase 4 문서의 1.0~3.4초는 질문과 조건이 달라 직접 비교하지 않는다).

## 3. 스트리밍을 붙이다 발견한 문제: 매 스트림마다 보안 예외 로그
- 문제: 스트림이 끝날 때마다 백엔드 로그에 `Unable to handle the Spring Security Exception because the response is already committed` 스택트레이스가 남았다. 클라이언트는 응답을 다 받았지만 로그가 오염됐다. MockMvc 통합 테스트도 같은 이유로 실패해서 발견했다.
- 원인: SSE 응답이 끝나면 서블릿 컨테이너가 같은 요청을 비동기(ASYNC)로 다시 디스패치하는데, Spring Security가 이때 인가를 다시 검사하고 인증 정보가 없어 접근 거부 예외를 던진다. 이미 응답이 나간 뒤라 처리하지 못한다.
- 해결: `SecurityConfig`에서 ASYNC 디스패치는 허용했다 (`dispatcherTypeMatchers(DispatcherType.ASYNC).permitAll()`). 이미 인증을 통과한 요청의 이어짐이고, 클라이언트가 ASYNC 디스패치를 직접 일으킬 수는 없다.
- 확인: 통합 테스트가 비동기 재디스패치까지 통과(수정 전에는 실패)하고, 같은 질문 8개를 실서버에 보낸 뒤 백엔드 로그의 예외가 0건이었다. 수정 전에는 스트림마다 찍혔다. 이전의 가짜 스트리밍도 같은 구조라 같은 로그가 났을 것으로 보지만 이전 로그를 확인하지는 않았다.
- 이전 구현은 응답을 UTF-8 바이트 240개 단위로 잘라 보내서 한글이 경계에서 깨질 수 있었다 (코드 기준 추정, 재현하지는 않음). 이제는 문자열 조각을 JSON으로 보내 이 문제가 없다.

## 4. 테스트 (175개 → 188개, 줄 커버리지 91.1%, 분기 73.1%)
- `AnthropicStreamTest`(6): SSE를 읽어 글자 조각과 도구 호출 시작을 전달하고 조각난 도구 입력 JSON을 합치는지, 요청에 `stream: true`와 키·버전·Accept가 실리는지, 입력이 없는 도구 호출, HTTP 오류(키 비노출), 중간에 끊긴 스트림, 스트림 중간의 error 이벤트
- `ChatStreamTest`(6): 상태 → 조각 순서, 도구 호출 전 문장은 reset, LLM 없이 규칙 기반 한 번에 전송, 부분 전송 후 실패하면 reset 뒤 규칙 기반 답변, 연결이 끊기면 모델·도구를 더 부르지 않고 폴백도 보내지 않음, 비스트리밍 경로는 기존 호출 유지
- `ApiSecurityIntegrationTest` +1: 스트림 엔드포인트가 `delta`, `done` 이벤트를 순서대로 보내고 비동기 재디스패치가 예외 없이 끝남

## 한계
- **운영 환경(Render, Cloudflare Pages)에서 스트리밍이 조각으로 도착하는지는 확인하지 못했다.** 중간 프록시가 응답을 모아 한꺼번에 보낼 수 있다. 서버는 압축 대상에서 `text/event-stream`을 제외해 두었다. 배포 후 챗 화면에서 상태 문구와 글자 흐름이 보이는지 확인해야 한다.
- 실제 브라우저 연결 끊김 상황은 직접 재현하지 않았고 단위 테스트로만 확인했다.
- 스트림으로 보낸 조각에는 비스트리밍 경로의 공백 정리(`TextSanitizer`)를 적용하지 않는다 (스트림은 모델이 준 글자를 그대로 보낸다). 시스템 프롬프트가 마크다운 없는 평문을 지시한다.
- 스트리밍의 지연 측정은 8개 질문, 로컬, 기상청 대역이다.
